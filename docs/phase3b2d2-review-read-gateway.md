## Selected architecture

Use a purpose-specific SECURITY DEFINER function whose NOLOGIN owner owns NO application tables and has selected-column SELECT only. Unlike the capture write-owner proposal, this read design does not require review-table ownership and does not conflict with the earlier prohibition on procedure owners owning application tables.

Proof signature:

    itw_read_poc.inspect_v1(action text, request_id uuid, revision_id uuid,
                            expected_version bigint, payload_sha256 text) RETURNS jsonb

No actor ID, batch ID, SQL identifier, evidence selector or arbitrary query is accepted. Revision determines its batch server-side. Action is limited to start/edit/submit preflight and review/return/reject preflight; all remain diagnostic only. Registration, APPROVE, REVOKE, promotion and unknown actions are disabled.

The function returns only a fixed denial code or writes_enabled=false plus a request fingerprint, or historical event ID and CURRENT version/state. A historical response is not an original durable write receipt, and no response can authorize a subsequent write. Denials for inaccessible/missing revisions and independent-review failures share ACCESS_DENIED. Another actor's event is denied even within an otherwise scoped batch.

## Authentication and scope

The synthetic proof uses actual PostgreSQL LOGIN authentication: session_user maps to a trusted administrator-owned principal record. Each synthetic login has a separately generated ephemeral password; passwords are not persisted in evidence. current_user inside the definer is not treated as the actor. Custom GUCs and request-body identity fields are ignored/rejected; runtime has no mapping-table mutation rights, no owner membership and no ability to assume another proof principal.

A second administrator-controlled table grants explicit actor/batch scope. Global capture/prepare/review permission is not automatically access to every batch. Independent review excludes uploader, creator and current/inherited contributors; inherited membership relies on unchanged 0003 participant-inheritance integrity.

These mappings prove database-principal isolation only. They do NOT authenticate a human session behind a shared Django database credential. The actual shared runtime has no principal mapping and returns IDENTITY_VERIFICATION_UNAVAILABLE even when granted gateway EXECUTE. The isolated Python adapter also refuses calls by default before any SQL. Its explicit isolated-db-principal mode is a test mechanism, not a production identity flag.

A production integration needs a vetted independent session broker/attestation verifier binding actor, audience, deployment/database, action, revision/batch scope and exact request fingerprint, with expiry/revocation/replay policy. A broker must independently validate the session, not sign a caller-selected user ID. There is no such deployed verifier here. Do not map the shared Django LOGIN to a powerful human user.

PostgreSQL recommends secure search paths and controlled grants for definer functions. [PostgreSQL 17 CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html).

## Locks, canonical bytes and errors

READ COMMITTED only. The function obtains advisory transaction lock (73921,2), then rechecks principal, active status, exact direct/group permissions, scope and independence with fresh queries. It performs no SELECT FOR UPDATE or DML. Production permission/scope/key writers must use that lock BEFORE row locks; only a cooperating-revocation race is proven, not comprehensive production writer coordination.

The fixed B.1 request shape is rebuilt in sorted-key compact JSON and hashed with SHA-256. Every interpolated field has a bounded grammar (allowlisted action, bigint, UUID, lowercase digest); no general JSON canonicalizer is claimed. The Python adapter reuses B.1's bounded payload validator. Unicode payload bytes are hashed by the existing canonicalizer. Golden comparison against B.1 fingerprint construction passed.

The adapter sets lock/statement limits before the SQL call and exposes fixed errors only, suppressing driver diagnostics. Malformed native SQL UUID/type inputs can still raise driver errors; they must pass through the adapter, never an exposed raw SQL endpoint.
